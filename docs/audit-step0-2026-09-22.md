## E. 缺少的功能及已发现问题

目标缺口：

- 主站 Home/Search/Cart/Orders/Account 五栏手机导航、指定首页栏目、最近浏览、独立商品详情页与统一商品卡片。
- 数据库层分页/排序/多字段过滤搜索，明确品牌/适配型号/keywords；语义搜索、pgvector、图片 embedding、临时搜索图清理、AI Chat 均未实现。
- 数据库购物车、主站收藏界面、主站完整登录/注册/找回密码、多地址、客户与 Auth 的稳定映射。
- MOQ 虽有列但无数据，当前 Web/mobile 主要下单链路不执行 MOQ；没有阶梯价格、重量、库存数量/预留机制。
- 主订单折扣/其他费用/币种/付款状态/交易记录/成本利润、全量操作审计、付款验证、完整物流时间线与发货日期。
- 报价 Ready、Accept、Payment Pending、Paid 的可靠统一状态机；当前 confirmed 后可以直接处理/发货，不检查支付。

优先问题：

1. **旧报价金额信任表单。** `src/app/admin/orders/[id]/actions.ts` 的 saveOrderQuote 直接读取 product_subtotal/grand_total/paypal_fee/paypal_collection 并写库；手工订单有同类行为。虽有管理员密码检查，仍不满足“服务端统一算账”。
2. **重复浮点计算。** AdminOrderProductDetails、ManualOrderForm、订单保存/邮件等多处用 JS number、乘法和 toFixed。数据库 numeric 并不能消除写入之前的浮点误差。老订单明细缺少快照价时还有回退实时规格价的显示逻辑，会影响历史金额稳定性。
3. **报价操作边界不一致。** saveOrderItems/persistQuote 对 mobile 订单有限制，但 saveOrderQuote 没有相同限制或订单状态检查，可能越过已确认报价保护；发报价邮件路径在持久化失败后仍可能继续发送，应统一事务和失败处理。
4. **身份与权限不足。** 后台共享密码出现在 URL/表单，没有独立管理员用户和审计身份。Web /api/orders 无账户登录，按用户提交邮箱匹配并更新客户资料；这不能作为账户归属证明。getLinkedCustomerId 还接受 expired token，需按业务边界收紧。
5. **上传不足。** inquiry-images 无登录/限流保护；当前仅检查 image/* 和 8 MiB，信任文件声明 MIME/扩展名，允许范围过宽；随机名使用 Math.random，未见文件内容校验或临时清理。现有询盘图是长期公开对象，不能直接当图片搜索临时存储。
6. **RLS 不能只看开关。** 26 张表均开启 RLS；orders/customers/order_items/mobile profiles/events 走服务端授权路径；sole_* 有 owner/admin 策略。但多张旧表仍给 anon/authenticated TRUNCATE/TRIGGER/REFERENCES 权限，需要通过非破坏性 migration 收紧。未尝试这些操作，也不能据此声称匿名用户已能通过普通 REST 删除数据。
7. **数据源重复。** products vs variants 价格字段、mobile_customer_profiles vs sole_profiles、orders vs sole_orders 并存。当前代码以 variants + orders 为主，不能新建第三套。
8. **库存不是数量库存。** stock_status 只能判断有货/缺货/预订，不能据此展示数量或承诺实际库存。
9. **检索扩展性。** 主站取全量商品再 contains，缺少数据库分页和多词匹配；当前规模可用，但不能等价于目标“white sneaker sole”稳健检索。
10. **本地工具与 lint 阻塞。** 默认 Homebrew Node 缺失 libsimdjson.29.dylib；副本 Python 虚拟环境未被 eslint 忽略，导致额外解析错误；样本目录页面存在内部 a 链接错误。
11. **类型/迁移缺口。** Product 类型缺少线上 MOQ/currency 等列，OrderStatus 包含任意 string，缺少严格状态约束；本地数据库测试不能覆盖所有线上漂移。

本阶段已修复问题：无，遵守“先审计，不开发”要求。上述均作为后续整改项保留。

- Resend、email_send_logs、邮件模板、样本文件、访客统计、现有四语功能全部保留。

## H. 实现目标系统的最小改造方案

1. **先锁定现有主链路。** 本仓库继续使用 products + product_variants + customers + orders + order_items；核对 sole_* 外部使用者，保留其数据/行为。用只读 schema 快照补齐设计基线，处理 migration 历史差异，禁止重新执行初始化脚本。
2. **第 1 步只做主站 Web UI。** 复用现有组件，在多语言路由中增加手机底部导航、首页/搜索入口和统一商品卡片，390px 优先、桌面兼容。相机入口可以先展示入口说明，不能伪装 AI 已可搜索；不改数据库，不把 Expo 当成新主站替代品。
3. **第 2–3 步完成商品与传统检索。** 增加独立详情路由，读已有 variants、MOQ 和图片字段；无价格则显示询价，无 MOQ 则不编数字。传统数据库搜索支持词拆分、SKU 精确匹配、属性过滤和分页；后续再加入合适的全文/模糊索引。
4. **第 4–5 步独立增加检索能力。** pgvector 仅负责候选排序，最终商品、价格和库存按 ID 回查数据库。视觉搜索只检索自有图；商品向量离线生成，查询图临时存储并配置 TTL/清理，不留永久副本。相似度须定义转换与校准，不能把任意 cosine 值直接宣称为“94% 正确”。
5. **第 6–8 步复用 Auth 与订单。** 购物车服务器查价、数据库持久化，收藏复用 sole_favorites；补主站 Auth 与地址；将 Web 下单统一到事务/幂等逻辑，提交只进入等待报价。兼容旧专属链接与询盘流程，但不能让未验证邮箱取得已有账户权限。
6. **第 9–11 步统一报价与算账。** 采用同一服务器 Money/Pricing 服务和数据库 numeric（或应用层十进制定点库），所有入口只能提交数量、单价、折扣、费用等受权限控制的输入；subtotal/total 由服务算出，UI 仅展示。确认报价冻结版本，后续改价产生新版本并撤销旧接受/支付资格。管理员修改数量/价格/增删明细与重算、事件写入应在同一事务完成。
7. **第 12–13 步接支付与物流。** 只有已发布且客户接受的报价版本允许创建 PayPal 支付；服务器读取总额，验证回调金额/币种/订单/版本/交易状态并幂等记账。人工 Invoice/Payment Link 单独标记并保留。确认付款后准备/发货，Buy Again 仅回填当前购物车，不复制旧价格。
8. **第 14 步再做 AI Chat。** 仅通过授权工具调用商品/规格/库存/购物车/订单服务，AI 输出结构化操作意图；数据库服务负责价格、库存、数量边界和最终金额。
9. **安全与测试贯穿实施。** 第 15–16 步是集中验收，但 Auth、ownership、role、金额保护和上传限制必须在各功能首次上线时就具备。用隔离测试用户 A/B、测试数据库、PayPal sandbox 覆盖你列出的 A–E 流程。

建议金额定义（待实现，避免原需求排版中的加减号歧义）：

```text
items_subtotal = Σ(quantity × quoted_unit_price)
total = items_subtotal - discount + shipping_charge + payment_fee + other_fee
revenue = total（本阶段不引入税费/退款等额外口径）
cost = product_cost + actual_shipping_cost + actual_payment_fee + other_cost
gross_profit = revenue - cost
```

当前数据库 `grand_total` 在旧链路中不含 PayPal 手续费、`paypal_collection` 才含费用；不能直接改字段含义影响历史单。应以版本化新报价逻辑和兼容适配明确“最终应付金额”，旧订单保留原有语义。运费、支付费和其他费用是加项，discount 是减项，AI 不参与最终金额计算。

状态最小兼容映射：`new`=Submitted/Awaiting Quote，`quoted`=Quote Ready，`confirmed`=客户已接受；新增独立 payment_status 后才能区分 Awaiting Payment/Paid；`processing/shipped/completed` 显示为 Preparing/Shipped/Completed。无需为展示名称立即批量改写所有旧状态。
